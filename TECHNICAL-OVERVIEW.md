Foundry: Technical Overview

Foundry is an agent-native version control platform built on Cloudflare. It answers one problem: when hundreds of AI agents work on the same codebase, a plain git push is a trust fall. Foundry replaces trust with a gate. Every push is treated as a proposal. Nothing reaches the shared branch unless a deterministic admissibility check approves it, and every decision is recorded with its reasoning in a permanent ledger.

The system has four moving parts. First, Artifacts repositories: Cloudflare-hosted git remotes where each agent works in its own isolated fork. Second, an event pipeline: every push fires a scoped event into a queue. Third, the gate worker: it consumes each event, looks up the agent's task ticket, evaluates the proposal against the shared branch, and writes a verdict — merge, reject, or conflict — into a D1 database. Fourth, the orchestrator: it creates task tickets, mints scoped access tokens, and dispatches agents into forks.

The gate enforces its rules in a fixed order. Rule zero is identity: a push from a fork with no task ticket is rejected immediately, with the reason recorded. This is deliberate. Anonymous work can never merge. Rule one is admissibility: the ticket's scope token is checked for mutation rights, layer range, freshness, and proposal validity through a small deterministic kernel. Rule two is conflict detection: the gate lists files changed on the fork since the fork point and files changed on the base over the same range. Anything touched on both sides is compared byte for byte. Real conflicts route to a resolver with both sides attached. They are never merged silently and never dropped quietly.

When the diff is clean, the gate performs the merge itself. It clones the base branch into memory, applies the fork's files as a single squash commit, and pushes the result back to the base repository. The verdict row then records the merged commit hash, the file list, the task and agent identifiers, and the timestamp. That row is the why-trail: for any change on the main branch, you can answer who proposed it, under what ticket, what the gate checked, and what it decided.

Two supporting systems extend the core. The overlap oracle consults a knowledge graph of every task in the system, so that two agents working in different forks on the same area are flagged as contenders even when their branches do not literally conflict. The trajectory ledger records decision histories in a portable schema, so the reasoning behind a merge survives beyond any single session or machine.

As of tonight, the full loop runs live on Cloudflare staging and production. Event subscriptions connect pushes to the queue, and the queue feeds the gate. This was proven in both directions. An unticketed push produced a recorded rejection stating that no task ticket exists for that fork. Ticketed agent pushes produced recorded merges, and the merged commits are present on the base branch. And the strongest proof is not a test at all: three agents built a real project in three ticketed forks tonight, and all three merged through the gate. The local suite holds at zero type errors and one hundred thirty-six passing tests, and the same ticketed flow runs deterministically on a laptop with no cloud account at all.
