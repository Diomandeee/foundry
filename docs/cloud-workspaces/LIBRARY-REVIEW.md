## Static findings and resolutions

1. A successful delivered-content pull did not establish reconstructability. Added explicit declarations while keeping all results `unknown` or `incomplete` and `ready: false`. Dependencies are declared but remain unverified; empty requirements and absent held evidence cannot imply readiness. Historical file observations are incomplete.
2. Browse grouping and normalized origins cannot prove lineage. New lineage is accepted only as explicit operator-supplied metadata bound to an exact version and approval reference. It is labeled `authorityVerified: false`; durable approval verification remains parent-owned. Legacy grouping stays a browse hint, never a canonical revision.
3. Changed workspaces lacked a local evidence path. Capture now uses the selected delivered base plus repeatable explicit `--include-new RELATIVE_PATH` additions. Only named files are visited; unlisted new work/history is not discovered or scanned. Missing named additions fail closed, while missing base files are recorded as deletions. Manifest entries bind full SHA/size/mode and added/modified/unchanged status; `includedNewPaths`, `addedEntries`, `changedEntries` and `deletedPaths` are hashed into the snapshot identity. No-follow component opens validate ownership, permissions and regular single-link files; selected metadata is rechecked before/after capture. Private staging, fsync and existing atomic no-overwrite publication remain local only, with failures retained rather than deleted.
4. Local snapshot immutability is application-level: read-only files/directories, content hashes and exclusive publication. It does not resist a privileged OS owner, and source capture is explicitly non-atomic. No WORM, canonical merge or complete repository backup is claimed. Stop writers and review changed source for sensitive edits before capture/publication. Metadata/stat observations are change detection, not build or secret-safety proof.
5. Broker HTTP contract was inspected in `workers/library-broker/src/index.ts`, its README, storage-broker types/README, library-jobs object types and compute transport authentication. Requests carry only existing `grantId`/`requestId`; actor/policy/provider identity/credentials are host-owned. Added bounded HTTPS client DI using an opaque credential reference and trusted issued-grant binding lookup. It does not mint grants, read credential files, copy credentials, run gcloud, issue SSH, or install an identity. HTTP redirects/errors do not expose bearer/provider details. Cached content must replay the authenticated scoped broker read before use; denied reads never fall back to another transport.
6. The broker response has bytes only, without provider generation headers. Exact generation/bucket/object authorization therefore depends on the trusted host independently binding the issued grant to the expected provider reference. Client hash equality is integrity evidence, not independent provider-generation proof. The existing broker checks its own object identity and bytes; this bridge does not invent the missing fleet namespace mapping.
7. Shared transport publication now checks the entire downloaded archive SHA and byte count, in addition to individual transport checks and the existing per-file restore verification. Private host destinations and raw restore exceptions are no longer returned through the pull API. The loopback server accepts no arbitrary destination, credential reference, grant, endpoint or filesystem-read path from HTTP. Existing captured source path listings remain part of the catalog browse model; there is no raw workspace file route or snapshot HTTP route.

## Exact broker stop

Hard broker limits are **1 MiB per immutable read, 8 MiB cumulative reserved/sealed payload, 32 lifetime grants and 128 lifetime read reservations**. Current fleet tar.gz archives and the existing roughly 12 MB catalog package exceed broker capacity. Fleet bucket/object references also do not establish the broker's authorized project/object-key namespace. The new client rejects objects above 1 MiB before network/cache access and requires a trusted exact binding for every smaller reference. It never issues a range read or invents a grant.

Chunk preparation/reassembly is now implemented as source, without executing it. `chunk_package.py` streams an explicitly approved local archive into <=1 MiB content-addressed `projects/PROJECT/objects/SHA` files, verifies the full original archive SHA/size and writes bounded unpublished manifest/descriptor/segment requirements. It never recompresses, extracts, publishes, uploads or changes the original archive. All prepared chunk/manifest generations are null and all preparation metadata is explicitly unpublished; original source archive generations remain actual recorded values. Optional supplied session metadata produces a prepared capacity plan only if all tasks fit. Failure retains private staging and refuses local no-overwrite publication. No package was actually prepared.

The source introduces `foundry.chunk-manifest.v1`, `foundry.chunk-package.v1`, `foundry.chunk-session-requirements.v1`, and `foundry.chunk-session-plan.v1`. The manifest binds the exact original archive reference, ordered chunk SHA/size/generation, project and approved target bucket. The published descriptor pins the final manifest SHA/bytes/positive generation at `projects/PROJECT/manifests/SHA`. Prepared manifests/descriptors cannot be read as published; an explicitly false publication authorization also refuses reads. Requirements bind the project, source reference, manifest hash/size and ordered task ranges. Actual chunk generation recording requires a new immutable manifest and descriptor after separately approved publication; preparation originals are preserved. There is no publication/finalization writer here.

`segment_requirements` reports how many independent durable namespaces are required under the hard caps. `plan_sessions` consumes explicit remaining byte/grant/read budgets; no initial capacity is invented. It counts the manifest and every ordered chunk occurrence, rejects reused authority/store/namespace aliases, binds namespaces to the archive hash, requires retained history and an explicit rollover review reference for multiple supplied namespaces, and refuses insufficient budgets. Its sequential plan can conservatively reject fragmented capacity. The plan hash excludes its own `planSha256` field. Budget observations and opaque review/storage IDs are not authority or atomic reservations: the host must verify the actual independent retained durable stores and approved exact plan. The code neither provisions nor resets/rotates/prunes any broker history. Actual server admission and grant budgets remain authoritative.

`ChunkReader` preflights pinned published metadata and the full supplied session plan before network reads. It verifies actual authenticated granted manifest bytes, then each actual granted chunk, then complete archive size/hash. Reassembly buffers only bounded chunks/manifest, with <=4096 chunks and <=4 GiB archive. Its single 30-minute monotonic acceptance deadline propagates through manifest/chunk reads into the concrete supervised transport; it is not renewed per chunk or inferred from a per-socket-operation timeout. Shared archive-cache verification runs again before publication, followed by existing extraction/file integrity checks. Cache hits also reenter scoped reads using a bounded discard sink. Trusted `broker_for` DI must approve the exact package digest/task/plan hash and stable request/grant identities against the real durable namespace and expected bucket/object/generation/hash/bytes; no catalog or browser claim creates that authority. The selected package/plan stays pinned per reader; actual current authorization remains parent-owned. Retries must not replace request IDs or namespaces to bypass consumed or unknown reservations.

`restore` invokes optional preflight for all selected source archive references before staging. Chunk preflight rejects reused broker authority/store/namespace IDs across archives, rather than independently assuming shared free capacity. The loopback browser's existing trusted reader factory can return `ChunkReader`; it exposes no package/grant/path controls to HTTP. Catalog sync accepts injected `ChunkReader` while still requiring a genuinely published catalog distribution descriptor, matching object hash/size, and all existing catalog/detail checks. Direct/SSH behavior remains separately explicit; chunk denial never selects either fallback.

Required activation evidence remains owner-approved package/provider namespace mapping, new real published chunk/manifest receipts, independently durable reviewed per-archive session namespaces and retained history, actual issued grants, approved exact capacity-plan/task bindings, current host credential-reference resolution and provider transport. Those resources do not exist by virtue of this implementation. No cloud repacking/uploading occurred. Broker-backed fleet browse distribution/pull is **not activated**, and runtime correctness is unverified. Existing local-catalog browsing needs no broker request.

## Final snapshot and broker review fixes

Explicit added-file capture is implemented, not left unsupported. The CLI appends one relative file path for every `--include-new`; the Python interface accepts `include_new`. At most 1024 distinct additions absent from the selected base are allowed; directories, globs, unsafe/colliding paths, missing additions, symlinks, hardlinks, special files and unsafe ownership/permissions fail closed. There is no automatic unknown-file scan. Unlisted files stay outside this selected-source snapshot and are untouched; the UI states the allowlist requirement without showing a secret/path denylist.

No reusable copy-policy filter was found in the inspected source paths, so `snapshot_policy.py` provides a conservative fallback. Known credential-store and protected-history/Git paths are refused before opening candidate content. Each selected candidate (base or added) must be UTF-8 text <=4 MiB, without binary/control content; total capture stays bounded to 4 GiB. Whole-file in-memory screening rejects private-key, credential/token, bearer, sensitive assignment, credential-URL and opaque-literal shapes before that file's bytes are written. No matched path/value/line/snippet/digest is logged or persisted on denial. Earlier accepted files may remain in a private failed stage. False positives and unknown/encoded secrets remain possible; this is not an attested secret-free or complete workspace backup. Source review and separate publication gates remain required; there is no unsafe bypass flag. No workspace/credential content was read and no capture was invoked here.

The lexical ancestry check was insufficient on case-insensitive filesystem aliases. `snapshot.py` now compares the source root's device/inode identity with every existing destination ancestor, before any staging creation, and repeats the check immediately before `mkdtemp`. The source root identity is checked on selected source opens. An alias such as differently cased workspace/destination spelling is refused when its ancestor identifies the source inode. This is static source review, not filesystem runtime validation; stop writers first. Arbitrary concurrent same-user namespace mutation is not made transactional by these checks.

`BrokerReader` now defaults explicit trusted endpoint/resolver/grant-lookup configuration to the concrete `BoundedHTTPTransport(endpoint)`. No browser activation flag, automatic credential resolver, deployed identity or default authorization success is added. The concrete module uses standard-library multiprocessing spawn, a private in-memory Pipe and one HTTPS POST with default TLS, no proxy discovery/redirect/retry/debug logging, and no credential payload in worker argv/env/files. Response body cap is <=1 MiB; returned headers are allowlisted and non-200/redirect/error bodies are suppressed. Request/response IPC frames are bounded to 64 KiB/2 MiB, with nonblocking parent descriptor reads/writes and deadline-aware wait/poll loops; readiness never leads to an unbounded `recv_bytes` call.

The parent accepts a response only after its exact worker is confirmed dead with a successful exit before the absolute monotonic deadline. On failure/expiry it sends TERM/KILL only to that owned worker and uses bounded 0.25-second joins for each stage. Late bytes/success are refused; unconfirmed startup/stop remains tracked and retains occupancy. At most two supervised HTTP workers per parent can occupy slots across transport instances. Python spawn may also use its standard interpreter resource helper; this is not a quota over every OS process. Kernel/start/scheduling stalls cannot be universally preempted, and error shutdown can consume a cleanup window after expiry. No physical provider-stop receipt or native attestation is implied. Buffered response `read/close` checks the pinned deadline without a live child behind it. Alternate injected ports remain trusted host proof gates; arbitrary blocking callbacks cannot acquire a timing proof through post-call checks.

Final exact-1-MiB readback: `BrokerReader` passes `max_response_bytes=reference["bytes"]`, consistent with `bounded_http.MAX_BODY == 1024**2`. The child reads at most the remaining accepted body allowance plus one byte to detect oversize, rejects an over-cap body and never returns that probe byte as a valid oversized response. The parent validates the returned body cap, and `BrokerReader` separately verifies full SHA/size in memory before any broker content reaches cache/staging. This is static contract consistency evidence only, not an executed 1 MiB transfer.

Concrete default support is unfrozen Python 3.10+ on macOS/Linux with a trusted import-safe file entrypoint; interactive/frozen/other-platform or post-parent-fork use is refused. Constructor/import starts no HTTP worker. No Python imports/probes, HTTP requests, spawn/terminate/kill/join operations, tests, builds, typechecks, service starts, installs or cloud actions were invoked during implementation. Native attestation, current authorization and project-scale readiness remain explicit **parent-owned HOLD**.

## R5 cache budget static review

The prior cache retained archives without an application quota and unlinked private failed download temporaries. `cache_budget.py` now enforces a fixed default **20 GiB** admission limit centrally in `CloudReader.fetch`, including direct, SSH, broker and chunk reassembly. No transport fallback bypasses the policy. New download/reassembly admission happens before transport calls or creation of the staging file. Cache-hit broker reauthorization also requires a complete inventory/capacity observation; unknown/over-limit capacity is not treated as free space.

Inventory is metadata-only, nonrecursive and bounded to 4096 managed files and a two-second checked interval. It accepts only current-user-owned, regular, single-link, non-group/other-writable hash archives and `.download-XXXXXXXX` temporaries, each no larger than 4 GiB. Unknown entries, subdirectories, links, special files, invalid owners/permissions, changing observations and unavailable allocated/free-space data fail closed. Root/ancestor symlinks, changed directory identity and unsafe ownership/permissions are refused. File metadata and directory signatures are rechecked to detect ordinary concurrent changes. Native filesystem calls cannot be preempted by the interval checks; filesystem behavior is unverified.

Accounted usage sums `max(logical bytes, allocated blocks * 512) + 4096` per managed file and root directory. A new archive reserves its full expected size rounded to the observed allocation unit, a file-entry allowance and an extra allocation unit for directory growth; actual filesystem free space also needs that amount plus a 64 MiB margin. A nonblocking exclusive directory `flock` remains held through all checks, streaming, verification and cache publication, so cooperating processes cannot spend the same free quota. The byte wrapper refuses oversized writes before they reach disk. Complete metadata rescan and full SHA/size verification precede atomic no-overwrite rename of the one staged archive; there is no duplicate cache archive allocation via hardlink/copy and no unlink. Failed/ambiguous partials and corrupt cache objects stay in place and remain charged. There is no automatic eviction, deletion, truncation, repair, stale-lock removal or history cleanup.

New read-only `GET /api/storage` and inherited `reader.cache_metadata()` report actual metadata observations only: policy limit, accounted/logical/allocated bytes, managed/partial counts, remaining quota, free filesystem bytes and observation time. Browser inputs cannot select a path or limit. The trusted reader's cache root must match the configured storage root; an initially unconfigured injected factory may establish its own root on the first valid pull attempt. No root path, filename, content, secret/reference value or raw filesystem exception is returned. No credentials or cloud client are needed for the metadata route. The UI adds a storage view and refresh button, and refreshes during existing pull-status polling.

During an exclusive writer, the metadata API reports `unknown/cache-busy` with null usage/reservation/free-space fields. Missing/unconfigured/unsafe roots and unknown capacity similarly stay unknown; policy limit remains 20 GiB. Zero active reservation is reported only with a successful shared-lock observation that excludes cooperating writers. Reported remaining quota is not an admission guarantee for an unspecified future archive. **No cache inventory, measurement, download, reassembly, browser session or runtime check was executed in this session**, so there are no measured cache totals in this receipt.

Remaining boundaries: application budget is not an OS quota or protection against an OS owner/noncooperating writer. All cache writers must use this locking/admission implementation; stop/upgrade old clients before activation. Directory-flock, fd-relative inventory/statvfs, exclusive rename, durability and accounting behavior on the selected local filesystem remain runtime gates. Unsupported platforms/shared filesystems fail closed rather than use an unlocked/unbounded fallback. Workspace restore staging, prepared chunk packages and local snapshots are outside the cache quota and retain their separate bounded/headroom behavior. Owner cleanup remains explicitly gated and is not implemented. The policy has no browser-controlled override.
