# Linux workspace isolation — local source delivery, 2026-10-18

**Implemented and source-reviewed; compilation, tests, independent acceptance and activation remain pending.** The supplied composition covers one owner-mediated Linux pilot attempt. It does not claim an installed worker, an unattended repeat-job service, or a completed Foundry fleet.

## What changed

The previous Linux path mounted input/work directories controlled by the same account that held controller credentials. Restoration/publication required an unspecified `ManagedTreeSeal`; no implementation could exclude other same-UID writers. The replacement does not invent that seal. A narrow root broker owns staging, an allocated workspace filesystem, Docker access, containment and immutable output capture. The unprivileged controller keeps Foundry transport and scoped broker access. Build processes receive neither credentials nor sockets.

The old `LinuxContainerAdapter.prepare/start` now always refuse. The old implementation was removed rather than leaving callable private bypasses. `BuildWorkerController` requires the concrete `LinuxIsolatedRuntimeAdapter` for Linux, just as Apple jobs require the concrete VM adapter. Existing callers/tests that depended on arbitrary Linux adapter injection need migration during the separately approved validation phase; no passing-test claim is made.

## Supported limits and deliberate exclusions

- Native x64/arm64 Linux; owner-vetted digest-pinned OCI images; offline npm, cargo and CMake recipes inherited from the parent profile.
- v1: at most 128 files/chunks; v2: at most 8,192 files, 2 GiB total, 64 MiB/file, and the existing authority ceiling of 128 required paths. ASCII canonical relative paths only. Existing finite namespace quotas still apply; no namespace creation/rollover or budget bypass.
- Existing parent profile ceilings remain 24 selected outputs and 7 MiB combined output/log bytes. The protocol's structural ceiling of 31 chunks does not increase those approved limits.
- Ordinary unsigned output files only. Apple bundles, signing, archive distribution, arbitrary directory archives, network dependency fetch and general interactive SSH are outside this adapter.
- **One owner-mediated attempt per broker invocation.** Even successful attempts retain the root slot, socket, frozen cgroup, mounted disk, captures and journal. No automatic retry, replay, restart, unmount, removal, slot reclamation or second-job admission is supplied. Sustained unattended reuse requires a separately reviewed reconciliation/release policy; it must not be described as already delivered.
- The controller and root runtime are trusted host components. This is not protection against a compromised root administrator, daemon/kernel exploit, malicious owner-installed interpreter/stdlib, or deliberate modification of privileged policy/resources during an attempt.
- Deployment must keep controller/broker in the same Linux time namespace and use the approved non-suspending VM configuration. Suspend before the local claim timing baseline and hypervisor clock behavior require operational acceptance; wall-clock synchronization is not used to extend leases.
- Physical filesystem/kernel IO can stall. Client deadlines do not falsely release physical occupancy; uncertain state remains quarantined. No fresh process, slot or credential is manufactured as recovery.

## Required owner-provisioned resources — none created here

`/var/lib/foundry-linux` and its `attempts` and empty `docker-config` directories: root-owned, private, canonical, ACL-free. `policy.json`: root-owned private bounded file. `/run/foundry-linux`: root-owned canonical directory; broker creates its UID/GID-restricted socket and readonly census. A dedicated root-controlled cgroup-v2 `foundry-builds` parent must have cpu/memory/pids controllers delegated to this broker, not to the build account. Docker must use cgroupfs and expose only a root-only local socket at `/run/docker.sock`; changing an existing shared daemon is not approved.

Installed fixed client paths: `/usr/bin/python3.12`, `/usr/local/libexec/foundry-linux-isolation.py`, each with actual SHA-256 pins. Root policy also pins `/usr/bin/docker`, `/usr/sbin/mke2fs`, `/usr/bin/mount`. Installed files/ancestors must be real canonical files/directories, root-owned, non-writable by other users and ACL-free. A source hash is not an installed runtime receipt. The full interpreter/stdlib and Docker/runtime/kernel remain owner-trusted dependencies. Mount the approved workspace disk at the root-private broker namespace; controller journals may remain on the smaller OS disk. No mount or disk configuration was changed here.

Policy schema is enforced by `load_policy`: version, controllerUid/Gid, distinct buildUid/Gid, maxWorkBytes, reserveBytes, executables hashes, and up to 32 profiles keyed by local recipe hash. `linuxIsolationProfile(binding,maxInputBytes)` produces only the profile data to review; it never installs a policy or approves activation. Existing real enrollment, scoped provider maps, capacity, profile approvals and `host.allowActivation` are still prerequisites.
