# M3 deferred acceptance — NOTHING EXECUTED

Every item below requires approval before running. Compilation/tests, installation/provisioning, VM/helper operations, provider writes/spend, credentials and cleanup are separate gates. This list is a protocol, not executable tests or successful receipts.

1. Compile/typecheck the changed TypeScript and native Swift/Python sources; run required existing gate checks only after test authorization. Confirm additive VM approval table/triggers on the actual supported transaction store and strict old/new protocol refusal.
2. Provision reviewed installed helper hashes, dedicated host/guest users, offline guest image and exact toolchain. Observe capability inside the guest, stop it, preserve the actual observation/boot SHA and accepted descriptor. Confirm host Xcode differs without affecting guest matching.
3. Demonstrate missing owner VM approval, wrong revision, missing/changed descriptor, incompatible SDK/macOS/architecture and unsupported memory/duration all defer placement. Confirm Pi cannot become eligible.
4. With a real broker-approved complete source, verify a single host reservation exists across claim, preparation, stage, VM, intake and publication. Demonstrate generation/hash/source drift, undeclared files, links/mounts, corrupt receipts and over-limit inputs refuse.
5. Observe actual persistent staging request. Separately approve and invoke owner I/O. Check partial/private/public receipts, atomic exclusivity, no overwrite, actual mounted tree and current lease before launch. Never count helper stdout as acceptance.
6. Observe whole-boot hash, VM current permits, runner hash and actual guest toolchain; run one supported unsigned offline recipe. No helper exit or output placeholder may satisfy success.
7. Confirm whole-VM stop and durable observation before output hashing; owner intake copies the exact stopped backing file, mounts only the copy, and returns complete bounded output/log lineage. Corrupt/failed/absent result never produces Exit code 0.
8. Exercise cancellation/renewal loss during stage wait, boot hashing, physical start, guest execution, intake wait, packaging and stage HTTP. Exercise sleep, abrupt client loss, uncertain callback state and restart. No late artifact/permit/request can reopen the attempt. Uncertain local state retains quarantine, even when some authority work was accepted.
9. Exercise duplicate controller requests and concurrent claim/start; inspect the single reservation, command identities, actual reported stop, actual manifest grants and independent verifier. Failures in journal append/finalize remain visible and prevent automatic reuse.
10. Demonstrate image/guest-capability change fences renewal, revoked enrollment denies broker/authority access, wrong project outputs refuse, and an expired local fence cannot stage stale results.
11. Observe VM-root disk accounting and incomplete/private/mounted inventory behavior; establish approved reconciliation/cleanup before another admission. Do not remove originals, arbitrary caches, simulator/SDK data or existing project folders.
12. Exercise poll→claim census pacing, installed-source consistency and actual operator UI. Verify prepared/installed/running/staged/verified/activated statuses against evidence. Only after these acceptance results and required integration reviews may progressive R7 activation be proposed.

Retain failed artifacts/journals and exact source/installed hashes. Never infer that M3 implementation has proven any of these scenarios.
