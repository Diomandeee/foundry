# Broker implementation and source review

Local source candidate; HOLD runtime acceptance/integration. No component described here was instantiated or invoked during this work.

## Concrete implementation

- `packages/storage-broker`: a distinct persisted online namespace mode beside the unchanged synchronous API. Online issue/read accepts caller cancellation; remote observations and provider reads are bounded. Concurrent duplicate online flights reject busy rather than sharing cancellation; exact completed requests can replay only after fresh authorization. Provider uncertainty and resource occupancy remain retained.
- `workers/compute/src/authority.ts`: authenticated owner `/v1/builds/access` validates a fresh request nonce and returns exact environment/authority/epoch. Build access commits clock/expiry maintenance before observing denial, so a read-side clock jump cannot disappear and revive an expired attempt.
- `build-online.ts`: fixed HTTPS origin, server-only credential resolver, random request nonce, 64KiB response bound, 5s monotonic deadline, no retries/redirects/cache. Complete compute tuple, project and profile must match. Short remaining lease and transient heartbeat staleness deny the current operation without permanently revoking it. Permanent fences are explicitly classified by authority state. No remote HTTP snapshot is represented as a synchronous global mirror.
- `build-host.ts`: immutable scope/namespace policy binding; separate supplied control/broker SQLite databases; exact schema/binding recovery; bounded admission; actual grant intents before issuance; real broker receipt before exposure; local per-grant deny before cross-DB delivery; exact command-key/payload revocation journal and unchanged actual receipts. Explicit bounded `reconcileOnce` retries deliveries and refreshes at most 32 grants; no daemon/interval is started. A network failure stays uncertain.
- Capacity reservations have stable operation keys and exact-need replay, including lost replies. Explicit receipts reach the writer and issuer. No mutable ambient current reservation, refund, pruning or automatic namespace reset exists. Output/log chunks and one result manifest reserve their combined overhead before any provider writes; staging reuses that debit.
- `gcs-build-host.ts`: composes the existing actual create-only/GCS pinned-read adapters. Logical project is checked separately from the billing project. Provider identity remains a private managed-reference port; no account lookup or provider operation occurred.
- `build-namespace-set.ts`: a finite explicitly approved set (at most 512 supplied DB pairs). Recovery searches all immutable operation histories, including inactive members. An operation already bound to an inactive member stops there; a new unrelated operation may use an active approved member. Actual DB/history errors never become absence. Exact prior debits are reused; conflicting histories fail. No dynamic namespace creation or quota rollover.
- `claim-inputs.ts`: a concrete post-claim resolver for at most three explicitly owner-approved job/generation slots. Policies pin job, input hash, server/local profile hashes, environment, authority, epoch, worker and incarnation; namespace templates pin the approved objects and supplied DBs. Only the actual attempt compute tuple is filled from the private controller-validated context. Rebinding the same slot to another attempt fails in memory or at durable namespace recovery. No guessed capability, preclaimed attempt, raw token or operator credential is used.

## Findings and dispositions

The first independent broker report requested five repairs: transient denial classification, lost reservation replay, cancellation propagation, false command-bound revocation acknowledgments, and a legacy-only observation regression. All were repaired in source. The second report confirmed those mechanisms and found three remaining integration issues: missing HTTP host typing, inactive namespace coupling, and unlinked preliminary HTTP refresh cancellation. Those were repaired as well; the final bounded review report records its observed source checkpoint.

The first input/runtime review found that post-claim scope resolution was missing, the actual working-source copy was not independently verified, hydration could exceed the tighter controller cap, and two equal-size roots could split the snapshot/provider binding. Current source resolves after the actual claim, uses the minimum cap before hydration/materialization, verifies both the immutable input and actual npm/cargo working-source tree, and binds provider-ref hash plus authenticated bytes to snapshotHash before version dispatch. See the corresponding final input review.

## Remaining boundaries

This is a distributed authorization check, not instantaneous global revocation of already delivered bytes. The final successful online observation orders each response; later revocation cannot recall it. Local durable deny markers block immediately once installed. No eventual mirror or stale snapshot is substituted for a required online check.

Actual host configuration/DB durability, independent credentials, provider permissions, exclusive managed-tree sealing, disk headroom, namespace approvals, catalog/chunk publication and runtime validation are still prerequisites. Input routing is incrementally admitted per immutable object; there is no atomic reservation of an entire arbitrary project. Failed later admission retains partial evidence. No operational namespace, credential, policy approval, provider generation or stop proof was created as implementation evidence.

Native full termination proof is still absent and native placement is blocked. Required-input lists above 128 cannot be approved through the current authority contract; v2 preserves them without truncating into a false approval. Output pilot limits are unchanged. Existing inherited integration HOLD findings are not closed by this batch.
