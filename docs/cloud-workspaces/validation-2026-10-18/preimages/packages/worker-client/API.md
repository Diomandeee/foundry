# Bounded host client API

`boundedStep(config: HostConfig, ports: HostPorts, signal?: AbortSignal): Promise<Summary>`

Config: fixed bare HTTPS `origin`, opaque `credentialReference`, enrolled `identity`, owner-provided `expectedEpoch`, `revision`, `incarnation`, stable `stepKey`, runtime-branded `profile`, `ttlMs` (1000..60000), `httpDeadlineMs` (1..30000), optional `heartbeatRefreshMs` (default 1000ms; owner must choose >= authority minimum heartbeat interval and strictly below its freshness window). General CPU and RAM allocations must EXACTLY match the authority workload reservation and fit approved identity. Edge (zero CPU/RAM/devices) only heartbeats. Config is snapshotted at entry; profile remains branded. Identity field order and device field/order differences are normalized before binding, sending, and comparing; devices sort by ID. No URL or command comes from work.

Ports: `HostFetch`, `credential(reference)`, `HostJournal`, runtime `runBoundedJob(plan, signal?)`, optional `now`. The trusted runtime must be a `WorkerRuntime` with durable `NodeStagingPort` or equivalent exclusive durable marker, bound to the SAME branded profile. HostFetch explicitly preserves Node `credentials:'omit'`, `redirect:'error'`; do not implement an adapter that follows redirects or attaches cookies. Credential resolution is inside the HTTP deadline; the resulting bearer is used only in the authorization header. No credential, raw remote error, artifact reference, or lease capability appears in Summary.

Summary kind: `heartbeat`, `idle`, `uploaded` (terminal); `retry` (same step/config again after bounded caller backoff); `blocked` (explicit owner investigation required). There is no retry loop or daemon. Network/deadline/stream/JSON failures return redacted `http-unavailable`; HTTP errors expose only numeric `httpStatus` and a fixed allowlist of codes (unknown code becomes `http-NNN`). 401/403 and permanent 4xx including stale-epoch/sequence-conflict return durable `blocked`; 5xx, 408/425/429, heartbeat-rate-limited and heartbeat-stale return `retry`. Pending operation keys/sequences stay unchanged. Heartbeat-stale requests an independent liveness refresh on the next invocation. Caller MUST bound attempts and back off, including enrollment schema v2's default 1s minimum interval per worker. Do not rotate operation keys or advance sequence to evade rejection.

The durable journal prepares heartbeat/poll/upload keys and phase BEFORE HTTP or activation. Heartbeat and poll have separate monotonic heads, starting 1. Heartbeat has its own pending/acknowledged state, recorded lastSeen and durable refresh key. Before resuming poll/upload, and again before upload transport after execution, the client checks lastSeen independently of cached freshness labels. It replays any unacknowledged heartbeat, then can prepare the next heartbeat sequence/key without touching the pending poll/upload identity. At most two heartbeat requests per check (old replay plus fresh request) prevent an unbounded refresh loop. A refresh response loss replays that heartbeat exactly on restart. Actual workerd tests advance the authority clock beyond freshness after lost heartbeat and idle-poll responses and recover successfully. Expired work leases still fail closed; heartbeat refresh never extends a lease. Poll body is `{expectedEpoch,request:{key,sequence,ttlMs,profileHash}}`, where profileHash is the canonical digest of the host profile. Authority compares it with owner approval before claiming. The client independently verifies the returned digest. General-worker TTL must exceed profile timeout plus15000ms; infeasible values reject locally before HTTP and server-side before claim. Same step replays exactly; a new step is accepted only after previous terminal success. A poll response cannot advance to another poll until handled. Upload phase retains actual bytes and exact fence/body/key for response-loss replay. Successful terminal replay performs no HTTP or execution. Retained per-lease identities prevent repeat execution; history caps at 1024 attempts and fails closed. Use one journal root per credential for its full lifetime; never reset or share it between bindings. Credential reference must resolve to the same enrolled credential throughout that journal lifetime.

Before execution, client validates worker/workload binding, epoch/incarnation, generation, running state, expiry margin, exact CPU/RAM allocation, the approved pure summary specification, expected hash, and host profile. It writes running/unknown-stop evidence durably before invoking runtime. Restart at running blocks permanently; it never reruns, self-reconciles or fabricates a stop receipt. Runtime result must be completed AND inspected stopped for the matching identity, full container ID, and matching hash/byte bounds; only then are actual base64 bytes sent to `/v1/artifacts` with `exitCode:0`. Server seals the reference; client checks returned artifact hash and size. Upload success is staging only, never verification or workload completion authority.

`HostJournal.exclusive` must serialize across processes for the entire step. `save` resolves only after durable storage; absent/corrupt/ambiguous state must not reset. `NodeHostJournal(root)` requires an existing private, owner-owned canonical directory. Writes use exclusive 0600 temp files, file fsync, atomic rename and directory fsync. An exclusive directory lock survives crashes; it is deliberately never stolen. Save failure retains the lock. Owner must inspect runtime markers/containers and retained stop evidence before any stale-lock recovery; no automatic recovery API is exported. Local trusted filesystem/administrator and host credential provider are prerequisites. Journal contains a lease capability, so preserve private ownership and never log/copy it into reports. Abrupt crashes may require manual stop inspection; no actual container execution is proven by fake-runtime tests.

Exports: main `src/index.ts`; Node-only journal `src/node.ts`. No enrollment, device provisioning, installs, quota mutation, renew, verification, stop reconciliation, background scheduling, deployments, or external operations.


Managed approval contract: owner POST /v1/enrollment/profile approves `{workerId,revision,profile}` under the authority’s image allowlist. Approval is immutable per credential revision; profile changes require a successor revision and preserved fencing/stop semantics. Work replies require `profileHash`; it is stored with pending work and rechecked on ready recovery. A host profile digest mismatch is rejected by the authority before claiming, and independently by the client before runtime. TTL runway rejects before a request when infeasible.
