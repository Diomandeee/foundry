# Foundry R1 pilot/operator candidate

**Local source candidate. Not executed, built, installed, deployed or runtime-verified.** The owner stopped all tests/checks during this work. No command below was run as part of R1 authoring. Every operational command requires the matching approval; a code block or `--owner-approved-*` flag is not permission by itself.

The candidate composes the existing SQLite Durable Object compute authority, a bounded worker process, a separate verifier and a loopback operator interface. It supports one fixed `epoch-event-summary-v1` CPU job. `pilot-input.json` is explicitly synthetic; it is not a real Stacks event or chain eligibility claim. Execution and independent acceptance must come from real future worker/verifier operations, never from that supplied example.

## Immutable input and job scope

`pilot-candidate.json` records the canonical SHA256 of `pilot-input.json`. `inputSha256` in OperatorConfig pins the shared canonical JSON representation, **not raw pretty-printed file bytes**. The source parser requires `kind:synthetic-pilot-input`, matching environment and the actual existing event-summary schema. It calls the existing job planner only when a future configured submission/input-read occurs; no planner or handler was executed to author this candidate.

The supplied event uses fake indexed block IDs, transaction IDs and a testnet-format contract identity. These are inert CPU input, not permission to call a chain or claim that event happened. Input scope authority `pilot-input` describes the synthetic event-source namespace; required config `inputAuthorityId` pins this distinct identity and must equal the input scope. It is not the actual deployed compute Durable Object ID, which is separately pinned as `authorityId`. Both identities enter durable command binding. Browser submission and accepted-output views carry the validated synthetic classification, source namespace and canonical input SHA; no receipt converts this source into an observed chain event.

Host-enforced `allowedWorkloadIds` contains1..8 exact owner-approved IDs, and must match the verifier allowlist. Each workload uses CPU1/RAM128/maxOutput4096 for the supplied input. The approved worker profile must match CPU/RAM exactly and allow the output. A real actor cannot select a URL, raw specification, shell, template, principal, quota, profile or verifier through the UI.

Submitter quota is explicit; it is not granted as a submission side effect. The host saves a deterministic full authority command before sending. HTTP requestId is a browser correlation identity; the authority command key/intent remains deterministic per workload/binding. Reopening the page and correlating an identical scoped workload may return submitted/replayed against the original durable intent. It never creates a replacement command to evade a rejection. Submitted is not running, accepted or physically stopped.

## Private host configuration

All configuration values below are required schema/approval inputs, not active credentials/endpoints. There is intentionally no valid-looking operational config filled with invented image digests/host paths. Read exact parsers before preparing owner-managed files.

**OperatorConfig** (`operator-config.ts`): version1; actual bare HTTPS origin/environment/authorityId; sourceMode local-authority or remote-authority; loopback port1024..65535; separate operatorCredentialReference, ownerCredentialReference, submitterCredentialReference; actual submitterPrincipal and distinct verifierPrincipal; inputAuthorityId event-source namespace; existing private stateRoot; canonical inputFile and inputSha256; allowedWorkloadIds1..8; explicit actionsEnabled boolean. No config starts static unconfigured mode only; missing references do not create default sessions. `actionsEnabled:false` blocks submissions and owner-host mutations. Operator credential values equal to authority values are rejected at login. References are environment variable names, not bearer values. Mutation journals also bind private SHA-256 fingerprints of the resolved owner/submitter values. Each operation captures these values once, checks for reference reassignment after asynchronous boundaries and uses the captured token for dispatch. A mismatch blocks rather than adopting old intent under another principal.

**WorkerConfig** (`worker-config.ts`): version1, optional enabled(defaultfalse), actual target/env/id/epoch, exact already-enrolled identity/revision/incarnation, executor credentialReference, separate journalRoot/supervisorRoot, heartbeat refresh/minimum/freshness matching authority defaults1000/60000ms, httpDeadlineMs100..10000, bounded steps/retries/backoff/runtime. General additionally needs exact branded profile/imageAllowlist/cli/stagingRoot/ttlMs; cli.allowActivation must be true only after separate approval. Edge forbids the general field entirely, including null, and uses zero capacity/no devices. General profile CPU1/RAM64 or128, matching actual input; lease TTL (<=60000ms) and supervisor maxRuntimeMs must both exceed the composed full runway reserve 48000+profile.timeoutMs+4*httpDeadlineMs. Immediate physical-start admission separately requires 28000+profile.timeoutMs+3*httpDeadlineMs remaining against saved lease and supervisor wall/monotonic deadlines. Example arithmetic only: timeout5000/deadline1000 gives full57000ms and start36000ms, so TTL60000 can pass parsing; the defaults implied by generic libraries must not be assumed to pass. Slow OS/filesystem/daemon work can still exhaust runway. No renewal or timing guarantee is provided. Read actual parser for remaining limits. Use different private roots per separately approved credential lifetime while preserving old evidence. Worker journals bind configuration and credential reference names, so config changes reject old bindings; unlike the operator and verifier journals, worker journals do not fingerprint or locally detect replacement of a token value behind the same reference. Requests resolve the current value; remote authentication/revision/incarnation/identity fences remain independently enforced, but their rejection is not local token-rebind detection. Do not reuse worker roots across credential lifetimes, replace a reference value to recover old pending intent, delete state or automatically rotate roots. Any credential change requires the separately reviewed enrollment/recovery workflow and explicit owner permission.

**VerifierConfig** (`verifier-config.ts`): version1, optional enabled(defaultfalse), actual target/env/id/expectedEpoch/verifierPrincipal, distinct ownerCredentialReference/verifierCredentialReference, private journalRoot, exact allowedWorkloadIds, bounded HTTP/backoff/step/runtime limits. Discovery reads use owner role on the exact-ID /v1/operator/workload route; unrelated global feed windows never gate them. Saved pending verification replays after identity/credentials/epoch checks before discovery, so a lost success reply can resolve even after history growth. New VERIFYING intent uses verificationDeadline, not execution expiresAt/capAt. Actual verify uses verifier role. Owner alone cannot verify. Discovery visits one canonical allowed ID per step; maxSteps/runtime may stop before all IDs, and a restarted invocation begins that discovery order again. Size the approved finite observation window for the intended IDs; no eventually-complete/always-on verifier claim is made. Acceptance must match SQL receipt identity/fences/verifier, including actual seal-reference derivation. Worker uploaded state is never accepted evidence.

Private state is deliberately bounded. Operator intents max8; owner operations max32; verifier intents max128; worker/runtime histories also have existing ceilings. Shared file reads cap1MiB but inert canonical state serialization is stricter at256KiB/complexity limits. Actual capacity may be reached before row ceilings. No evidence pruning, automatic migration, credential-root rotation or stale-lock theft is provided.

## Operator journey and meaning of states

Login using the separate local operator credential. The UI reads actual owner-only durable feed through the private host bridge. It shows approved worker geometry, current enrolled freshness/revocation, quarantine, queue, attempts/leases, historical feasible-worker placement/rejections and immutable audit metadata. A successful authority read is not proof a worker is connected or executing. Hostname/OS/architecture/census-role details are not in the existing DTO and are not invented.

Submission is available only with healthy source/session, enabled actions and pinned input. Preserve unresolved request identity; do not start a different job to hide an uncertain response. Actual independently accepted receipts enable scoped text lookup. The authority point reader validates workload/winner/receipt/lease/staged artifact/sealed bytes; the bridge independently checks canonical base64/size/SHA256, exact pinned intended workload/principal/specification/resources/output policy and configured distinct verifier principal before returning plaintext. A same-ID receipt for another principal/specification is rejected. UI adds receipt matching and never reads arbitrary artifact references.

The view is bounded and read-only. Every family and placement candidate window discloses truncation. Audit pages show after/through/head/hasMore; they do not acknowledge the outbox or represent a separate durable archive. Full source events remain at authority. Matching ordering indexes and transactional family counters bound ordinary feed reads; actual plans/SQL syntax/trigger behavior/performance have not been executed or measured. First authorized initialization creates indexes and counts retained rows once for missing counters, which can be expensive. Schema additions are idempotent source changes with schemaVersion1, not an applied migration receipt. Owner status and operator reads observe enrollment clocks without persisting a tick; executor mutation authentication retains monotonic persisted time and duplicate-digest validation. Rendered UX has not been observed. Empty/incomplete/unavailable/stale are distinct; no fixture fallback.

## Stop, restart and recovery ownership

Worker completed-step budget, absolute deadline, retry and blocked state persist across restart. Restarting the same command/roots does not renew that lifetime: an edge maxSteps1 worker that completed its heartbeat returns worker-complete on restart without sending another. Ongoing coverage requires a separately reviewed successor/recovery plan that preserves all existing evidence; never delete state or automatically rotate roots to manufacture a fresh lifetime. Verifier invocation step/runtime bounds differ as described above; its per-intent attempt budget still persists.

SIGINT/SIGTERM tells a launcher to stop further work; it does not prove remote/physical cancellation. Worker client writes ambiguity before runtime activation and requires actual inspected stop evidence before upload. Private supervisor/client/runtime state must be retained. A crash or save failure can leave locks intentionally. Do not delete them, reset sequence, change credential binding, wipe state or rerun an uncertain container. Owner investigation must tie full container identity/incarnation and actual stop evidence to any recovery action.

Present null/malformed client journals fail closed; only an initially absent file is new state. General-worker HTTP admission holds at most four original operations in this process through cleanup, even if logical caller timeouts happen earlier. Saturation blocks new network attempts. The final local start callback runs after adapter path/socket validation and immediately before synchronous CLI spawn, but cannot atomically observe remote revocation or bound OS/daemon scheduling.

Core verification success itself quarantines the worker, increments its incarnation and retains quarantined reservations. Therefore one successful job does not make that credential/worker reusable. This pilot does not auto-reconcile stop or reenroll successors. Observe and resolve that state under a separately approved physical-stop workflow; never manufacture `stopReceipt` from expiry, UI state, CLI exit or missing container output. To establish both platforms, approve a separate fresh worker/credential path for each and retain actual execution receipts.

The actual approved image must match each host daemon platform; one tag or host label does not establish cross-architecture image compatibility. Node handler source is portable, but a produced platform image/manifest and matching digest must be established separately. Mac execution is not native macOS support. It requires an actually qualifying local Linux Docker daemon/VM and a canonical owner-approved Unix socket that meets all existing path/permission/isolation checks. Docker Desktop installation, socket aliases, cgroup/seccomp support and image compatibility are not established. Common group-writable or symlinked Docker socket layouts can reject on both Mac and VPS. Do not weaken or chmod a shared production socket from this runbook. Resolve an approved runtime arrangement before enabling general workers. Pi needs none of these executor prerequisites.

To roll back a pilot, first stop new submissions/polling through approved controls, preserve all pending/journal/container/seal/authority evidence, perform actual stop inspection where needed, and apply only reviewed configuration/service rollback consistent with persisted issuer/environment/managed-mode bindings. Rolling source back is not permission to recreate the database or clear quarantine. No stop/deploy/install/rollback operation was performed in R1.
