# Bounded owner-operated BUILD pilot

This is an executable caller of the existing Linux isolated-build and Mac VM
build-worker factories. It handles one explicitly named job/claim invocation,
not a service or polling loop. Import and preparation are inert. Actual
activation remains an owner operation with all existing operational gates.

**Current disposition: prepared/tested, activation HOLD.** No operational config,
installed hashes, source image identity, cloud object generation or credential
has been generated by this work. Test fixtures are synthetic and are never
operational inputs. No installation or deployment is performed by any command.

## Commands

Run from `/Users/mohameddiomande/Developer/foundry-integration/source`, using the
existing `node_modules`; no install is required or authorized. The variables
below denote existing owner-provisioned absolute private JSON files and the
receipt digest of matching explicit user approval. They are syntax, not supplied
configuration values.

```sh
node_modules/.bin/tsx tools/foundry-build-pilot/cli.ts --help
node_modules/.bin/tsx tools/foundry-build-pilot/cli.ts prepare --config "$OWNER_CONFIG"
node_modules/.bin/tsx tools/foundry-build-pilot/cli.ts run --config "$OWNER_CONFIG" --approval-receipt-sha256 "$ACTIVATION_RECEIPT_SHA256"
node_modules/.bin/tsx tools/foundry-build-pilot/cli.ts prepare-verify --config "$VERIFY_CONFIG"
node_modules/.bin/tsx tools/foundry-build-pilot/cli.ts verify --config "$VERIFY_CONFIG" --approval-receipt-sha256 "$VERIFICATION_RECEIPT_SHA256"
```

Only these argument shapes are accepted. There are no browser arguments,
executable module loaders, command overrides, provider switches or implicit
configuration locations. JSON files must already exist at canonical absolute,
symlink-free paths, owned by the invoking UID, private to it, under trusted
ancestors. Host config is bounded to 256 KiB plus the existing canonical-data
node/depth limits; verifier config to 16 KiB. Unknown/missing fields fail closed.

`prepare` validates and composes the actual factories and returns
`prepared-not-activated`, job/epoch and both profile hashes. Linux also returns
the existing `linuxIsolationProfile` **proposal**, without installing or accepting
it. It does not open databases, resolve credentials, discover installed helpers,
start a VM/container, or contact a provider. Mac construction establishes the
concrete CAS's process-local pin identity without connecting to its service.
`prepare-verify` validates data only and returns `prepared-not-verified`.

`run` requires both `localPolicy.host.allowActivation: true` and the matching
receipt flag. The flag is an owner confirmation marker; the launcher does not
verify approval provenance, hash the entire config into an approval, or grant
user authorization. Match the actual external approval to the complete config
before running. OS/architecture, real/effective dedicated UID/GID, existing
runtime host guards, installed pins, accounting, enrollment and broker checks
remain enforced.

## Owner config fields

`OwnerConfig` in `config.ts` is the complete typed data contract. Nested fields
are existing runtime/broker contracts, validated without a module-loading hook.

| Field | Required owner data / meaning |
| --- | --- |
| `version` | Exactly `1`. |
| `origin` | Canonical HTTPS authority origin only, no path, auth, query or fragment. |
| `activationReceiptSha256` | SHA-256 identifier of the matching explicit activation approval receipt. No default. |
| `executorCredentialRef` | Named environment reference for the enrolled executor bearer. |
| `accessCredentialRef` | Separate named environment reference for the owner-side online `/v1/builds/access` observer. |
| `verifierCredentialRef` | Separate reference name reserved for the independent verifier; run never resolves it. |
| `ownerPrincipal` | Actual broker owner principal identifier. |
| `profile` | Complete owner-approved `BuildProfile`: `version`, `projectId`, `kind`, `limits`, `recipe`, `outputPaths`, `trustedProject`, `workerOptInRequired`. Existing strict build validation applies. |
| `serverProfileHash` | Hash of the exact approved parent profile. |
| `localPolicy` | Existing `LocalRecipePolicy`: `host`, `pids`, `tmpMib`, `minFreeBytes`, optional owner-approved `cmakeConfigureArgs`. |
| `localPolicy.host` | `uid`, `gid`, `dedicatedBuildUser: true`, `allowActivation`, `inputBase`, `workBase`, `journalRoot`, plus Linux `imageExecutables` for the selected tool. Roots/accounts must already be provisioned. |
| `job` | Exact approved `BuildJob`: `id`, `projectId`, `inputHash`, `profileHash`, `maxAttempts`. The command performs one invocation regardless of the job's authority retry budget. |
| `claimKey` | Explicit stable owner invocation ID; no generated retry identity. |
| `claimPolicy` | Exact `environment`, `authorityId`, `workerId`, `jobId`, `projectId`, `inputHash`, `serverProfileHash`, `localRecipeHash`, `epoch`, `generation`, `incarnation`. No wildcard or invented attempt/capability. |
| `liveness` | `expectedEpoch`, actual `approvedIdentity`, `authority: {environment,authorityId,workerId}`, `revision`, `incarnation`, authoritative `initialEnrollmentSequence`, `initialCensusSequence`, `optedIn: true`, existing private `cacheRoot`. General CPU workers only; no GPU devices. |
| `maxInputBytes` | Explicit positive cap, at most 2 GiB; upstream storage/format limits still apply. |
| `outputs` | Exact profile output paths as `{path,classification}`; classification is `build-output` or `debug-symbols`. No signed publication. |
| `inputNamespaces` | 1–32 explicit read namespace records described below. Whole config bounds may reduce this maximum. |
| `resultNamespace` | Exactly one explicit publication namespace record. |
| `runtime` | Exactly one Linux or Mac record described below. |

Derive the two hashes from actual approved data using the existing
`approveParentProfile(profile, serverProfileHash, localPolicy)` API and its
returned `localRecipeHash`. Preparation cross-checks them; it does not accept a
remote claim as approval or invent missing local policy. Config paths are
owner-private host data, never browser input or remote build arguments.

Each namespace has exactly:

| Field | Meaning |
| --- | --- |
| `controlDbPath`, `brokerDbPath` | Distinct existing owner-private regular SQLite files, single link, private parent directories. All namespace paths are distinct. Missing files fail. |
| `approval` | `version: 1`, `namespaceRef`, `scope: {projectId,principalRef,namespaceRef}`, `profileHash`, `policyVersion`, `intentId`, `authorizationGeneration`, `expiresAt`, `publication`, `approvedObjects`. No preclaim `scope.compute`. |
| `approval.approvedObjects` | Exact generation/hash/size-pinned `ObjectRef`s, 1–32 for a read namespace; empty for a publication namespace. Every metadata/chunk read must be covered. |
| `approval.publication` | `false` for inputs; `true` for the single result namespace. |
| `gcs` | Existing `GcsHostConfig`: fixed `origin: https://storage.googleapis.com`, real `bucket`, matching logical `projectId`, named `credentialRef`, optional bounded existing GCS `limits`. |

All role references must be distinct; provider refs cannot equal the
executor/access/verifier refs. The existing environment reference resolver is
used only during operations. The JSON holds reference names, never bearer
values, service-account keys or SDK credentials. Distinct names alone do not
prove distinct underlying principals; server authentication and role separation
remain necessary.

Input and result namespace assembly are separately lazy. Before **any** DB open,
the launcher checks controller-branded context, complete exact policy, source,
job, input, both profiles, worker, epoch, generation, incarnation and actual
attempt/lease identity. Each awaited open is cancellation-fenced before and
after. Failed assembly is retained and never retried/reset. Input resolution
opens only input DB pairs; result resolution opens only the result pair.

The real `createClaimInputResolver` / `createClaimResultResolver` fill only the
actual post-claim compute binding and compose existing GCS reader/writer,
namespace selector, durable reservation, issuer and online authorization ports.
An existing empty SQLite file can receive its schema on authorized resolution;
this is a write operation. Nonempty recovery must match the persisted schema and
full immutable binding. No reset, rollover, path creation or cleanup exists.
Opened handles remain until process exit so late operations cannot use closed
handles. Native Node SQLite lacks atomic `create:false`; existence and identity
checks assume trusted same-UID administrators do not race pathname replacement.

Linux runtime fields:

- `kind: linux`.
- `isolation: {python,pythonSha256,helper,helperSha256}` with exact existing paths
  `/usr/bin/python3.12` and `/usr/local/libexec/foundry-linux-isolation.py` and
  actual installed hashes. Preparation does not claim those files exist.
- Existing root broker retained-one-attempt policy remains intact. No broker
  install, service start, slot reclaim or root policy acceptance occurs here.

Mac runtime fields:

- `kind: mac`; `executable: /Library/Foundry/bin/mac-vm-host`.
- `capability: {sha256,seal}`: accepted image capability and full existing
  `MacReadonlySealConfig`; capability root must match the digest.
- `sources`: 1–128 exact `{snapshotHash,seal}` accepted source-image records.
- Each `seal` supplies `helper: {path,sha256}` and `tree: {path,mountPoint,
  filesystem,fsid,mountSource,volumeUuid,rootDevice,rootInode}`, with optional
  bounded `maxOperationMs`. These are actual readonly image/installed guard
  identities, never filesystem guesses.
- `storage`: concrete CAS pins `python: {path,sha256}` at
  `/Library/Foundry/bin/cas-python` and `helper: {path,sha256}` at
  `/Library/Foundry/bin/mac-cas.py`.
- Explicit `maxBootBytes` and `maxOutputDiskBytes`, within existing aligned limits.
- Existing owner-mediated stage/intake mailbox acceptance and concrete CAS
  boundaries remain. The command does not mount images, accept mailbox requests
  as owner, create seals, or start the CAS service.

## Separate verifier config and atomic target contract

| Field | Required value |
| --- | --- |
| `version` | Exactly `1`. |
| `origin` | Approved canonical HTTPS origin. |
| `environment`, `authorityId` | Exact approved authority identity. |
| `expectedEpoch`, `attemptId`, `jobId` | Actual staged attempt, its job and authority epoch. Never inferred from a latest-job search. |
| `verifierCredentialRef` | Separate verifier environment reference; only this reference is resolved. |
| `otherCredentialRefs` | 3–35 distinct names covering executor/access/provider roles; must exclude the verifier ref. These references are not resolved. |
| `approvalReceiptSha256` | Matching explicit verification approval receipt digest. |

`verify` sends **one** authenticated POST to `/v1/builds/verify-target` with exactly
`{expectedEpoch,attemptId,jobId,environment,authorityId}`. It has no fallback to the
legacy `/v1/builds/verify` route. The parent's server change enforces this target
before mutation and replay. The accepted response is exactly
`{ok:true,verified:true,jobId,attemptId,source:{environment,authorityId,epoch}}`,
optionally adding `replayed:true`. Every identity is compared to config; unknown,
missing, oversized, cancelled or failed responses are unconfirmed. A 35-second
monotonic request deadline bounds the existing server's 30-second verifier.
The command never resolves an executor or owner bearer to finalize a result.

## Journey, exits and remaining gates

1. Owner prepares genuine configs from approved profile, identity, input object,
   namespace and installed-runtime records; `prepare` checks the inert assembly.
2. With matching external approval and provisioned runtime, `run` calls
   `controller.run(job, claimKey, signal)` once. Existing controller journals own
   durable attempt state; there is no auto-poll, requeue, recovery replay or service.
3. SIGINT/SIGTERM request cancellation; repeated signals do not force exit or
   clear evidence. The caller awaits controller trusted-stop/staging/quarantine
   resolution. Uncertain requests remain reconciliation work.
4. A staged result prints `staged-awaiting-verifier` (exit 0), **not verified**.
   `stopped-without-result` exits 3; reconciliation/failure exits 2. Preparation
   also exits 0, with its distinct non-activation state. No raw logs/capabilities
   are printed.
5. Independent owner-operated `verify` submits the exact atomic target with its
   separate credential. Only a matching authenticated receipt prints `verified`
   (exit 0). A cancelled/lost response is unknown, not proof of rollback.

**Broker reachability is an unresolved activation prerequisite.** Compute reads
published grants via `BUILD_BROKER_ORIGIN` / `BUILD_BROKER_CREDENTIAL`. This host's
scoped broker grants reside in the approved local SQLite namespaces. The launcher
exposes no listener or HTTP authentication configuration, copies no grant DBs,
and installs no service. A separately approved deployment must serve those exact
namespace records to the independent verifier with the matching grant principal.
Successful direct-host publication alone does not establish that route.

Parent-reported read-only R7 inventory: Mac1 about 29 GiB, Mac4 about 14.27 GiB,
Mac5 about 12.71 GiB free; required `/Library/Foundry` helper/CAS/image paths absent.
Those machines do not meet the 50 GiB plus job reserve. Selected GCP project
Compute Engine API is disabled. No API enablement or provider mutation was
performed. These gates remain HOLD; no installed config values are needed to
validate source preparation.

Supported: one named Linux isolated attempt or Mac VM attempt, existing scoped
GCS/SQLite brokers, bounded unsigned outputs, source-bound independent target
verification. Unsupported: arbitrary executable config modules, generic process
builds, signed archives, GPU census, services/autoloops, dependency installation,
credential provisioning, arbitrary URLs, remote path/argv overrides, namespace
rollover, owner mailbox automation, forced cleanup or simulated operational
success.
